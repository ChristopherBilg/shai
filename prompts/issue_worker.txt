## Constraints

- Create the pull request as a **draft**.
- The PR body must include `Closes #{{NUMBER}}` so the issue auto-closes on merge.

## Continuous Integration

After creating the draft pull request, verify that CI checks pass on the branch:

1. Capture the pushed SHA right after pushing: `git -C <clone-dir> rev-parse HEAD`, where
   `<clone-dir>` is the clone you made in the Objective step.
2. Poll SHA-aware instead of trusting `gh pr checks` alone: in the window between the push and
   GitHub registering the new run, `gh pr checks` reports the **previous** head's run, so a
   stale green run reads as success. Treat only entries whose `headSha` equals the relevant SHA
   as relevant:
   `gh run list --branch <BRANCH> --repo {{REPO}} --json headSha,databaseId,status,conclusion --limit 10`
   For repos whose CI triggers on `pull_request` rather than `push`, runs execute against the
   merge commit (`refs/pull/N/merge`), so their `headSha` is the merge commit, never the pushed
   head SHA — compare against the PR's merge commit SHA instead, fetched with
   `gh api repos/{{REPO}}/pulls/{{NUMBER}} --jq .merge_commit_sha`.
3. No entry with `headSha` == the relevant SHA (pushed SHA, or merge commit SHA for
   `pull_request`-triggered CI) means pending — CI has not started yet. If the branch has no
   runs at all (empty list), do not conclude "no CI" immediately: `gh run list` can be
   transiently empty in the registration window right after the push, and CI that lives outside
   GitHub Actions never appears in it. Poll a couple more times first (~60–90 seconds); if it
   is still empty, the repo likely has no Actions-based CI on this branch — stop polling early
   instead of sleeping out the budget, and note it in the PR body. Otherwise use the `sleep`
   tool to wait 30 seconds between polls, for up to roughly 6 minutes total.
4. A matching entry with `status: completed` gives the real verdict — read its `conclusion`.
   A green result for any other `headSha` is a stale run of the parent commit and must NOT be
   reported as the push passing. Any CI claim in the PR body must name the SHA the checks ran
   against.
5. If all checks pass on the pushed SHA, add the label `shai-review-dispatcher` to the pull
   request so it is automatically queued for review. If the label does not exist in the
   repository, create it first with `gh label create shai-review-dispatcher --repo {{REPO}}`.
   You are done.
6. If checks are still pending after roughly 6 minutes of polling, stop polling and update the
   pull request body to append a note that CI checks did not complete within the polling
   window, then stop.
7. If any checks fail:
   a. Find the failed run with the same SHA filter as step 2 (pushed SHA, or merge commit SHA
      for `pull_request`-triggered CI):
      `gh run list --branch <BRANCH> --repo {{REPO}} --json headSha,databaseId,status,conclusion --limit 10`
      and use the matching run's `databaseId`.
   b. Read the failure logs: `gh run view <RUN_ID> --repo {{REPO}} --log-failed`.
   c. Fix the failing code, re-verify locally with the `ci` tool where a check covers it, commit the fix, and push.
   d. Return to step 2 to re-check CI (re-capture the new pushed SHA in step 1).
8. You may attempt up to 3 fix-and-push cycles. If CI still fails after 3 attempts, update the pull request body to append a "## CI Failures" section listing each failing check, the relevant log output, and what you tried. Then stop.
